# 任务
你的任务是根据`大纲`将`洞察`和`数据表格`组织起来，生成一份结构完整、逻辑清晰的工程可研报告。

## 生成方法（强制）
1. 先在内部按大纲完成章节计划和证据分配，再逐节撰写；不要输出内部推理或计划草稿。
2. 每一节只使用工程背景、数据表、洞察、compare_rules 和 retrieved_claims 中与该节有关的证据。
3. 先确定安全硬约束结论，再写技术和经济比较，最后写综合结论；后续章节不得推翻安全结论。
4. 已经存在于数据表或 exact claim 中的结果直接引用，不重复计算；只有正文必须展示且数据中没有直接结果的真实派生过程才使用 `<calculate>`。
5. 三张核心汇总表和标准图表由程序自动插入。不得输出 `<visualization>` 标签，不得自行生成绘图代码，也不要复制三张核心表制造重复内容。

## 数值与溯源规范
- 原始、可精确匹配的数据按下方 `claim_protocol` 使用 `<claim>` 标签。
- 没有精确匹配 claim 的原始数值只能写普通文本，不得用 `<calculate>` 代替 `<claim>`。
- 由一个或多个原始值通过明确公式计算得到的派生值必须使用 `<calculate></calculate>` 标签。
- `<calculate>` 只用于展示真实计算过程或计算结果，不用于原始字段复述、证据兜底或格式化展示。
- **单位换算**：claim 标签内显示值必须与原始 value/unit 一致。元→万元/亿元必须用 `<calculate>`（亿元=`元/100000000`），禁止把亿元数值绑到元 claim，禁止用 `round` 处理数量级换算。
- **属性一致性**：`claim_id/source_path/path_to_value/policy/value/unit` 必须整体来自同一条 retrieved_claim，禁止拼接。
- 禁止输出 `formula: none`、`formula: 无`、`formula: 原样引用`、`formula: 直接引用` 或等价写法；如果没有公式，就不要使用 `<calculate>`。
- **严格格式**：`<calculate>` 是固定开始标签，必须原样写出完整的 `>`；所有字段必须写在标签内容中，不得写在开始标签内。
- **标识案例**：
    <calculate> input: construction_cost=108000000, operation_cost=5400000, i=0.07, n=20; input_source: construction_cost=claim_xxx, operation_cost=claim_yyy, i=compare_rules.metrics.annual_cost.default_inputs.interest_rate, n=compare_rules.metrics.annual_cost.default_inputs.years; formula: construction_cost * i*(1+i)**n / ((1+i)**n - 1) + operation_cost; output: 15594435.98 </calculate>

## 背景资料使用规则
1. 如果 `<background_context>` 非空，必须视为有效工程输入；不得因仿真节点命名不同而判定“未提供”。
2. “周边500kV电网接入点分析”必须综合使用背景资料、方案数据表、潮流结果、N-1校验结果、短路电流结果和 `retrieved_claims` 中可核验的真实数据。可以说明周边500kV相关节点、相关线路、电压等级、短路电流水平、断路器开断能力、N-1故障表现和潮流运行情况；不得仅因缺少地理资料而将整个章节写成“无法分析”。
3. 当短路电流结果存在 `bus_name`、`short_circuit_current_kA`、`breaker_current_kA` 等字段时，应选择具有代表性的关键节点进行定量分析；当N-1结果存在故障线路、过载线路和负载率时，应说明相关线路的N-1运行表现。引用具体数值必须遵守现有 `<claim>` 与 `<calculate>` 溯源规则。
4. 仿真报告中的普通故障节点不得直接表述为已经确定的候选接入点，应称为“周边500kV相关节点”或“重点关注节点”。
5. “接入系统方案拟定”优先依据背景资料中的方案思路与拟定方案；仿真 `modifications`/数据表用于补充真实接线与长度。二者命名不一致时，分别说明来源，不要互相覆盖，也不要因此整节留空。
6. 方案线路和节点信息必须优先使用 `parsed_proposals.json` 中真实存在的 `modifications` 数据。
7. 地理位置、站址距离、备用间隔、线路走廊和建设条件只能依据背景资料中的真实内容生成，不得根据电气仿真结果推断或编造。
8. 当背景资料为空但方案数据表、潮流、N-1或短路电流结果存在时，仍须生成电气层面的周边网架和方案分析。仅对输入中确实不存在的地理位置、距离、备用间隔、走廊及建设条件等子项标记“当前输入不足，未提供该项资料”。
9. 不得把方案生成指令、经济指标摘要直接当成接入点分析正文，但可以从中提取明确给出的工程目标、目标节点和约束条件，并注明其属于任务输入。
10. **禁止过度推断**：“具备物理连接条件”仅当 modifications 确实包含对应新增线路时才可使用；“位于重载区域附近/适合作为接入对象”仅当输入明确给出地理或电气邻近关系时才可使用；不得把仿真出现的节点自动认定为工程上适合接入的节点。

## 安全硬约束与最终推荐（强制）
1. 安全硬约束优先于经济排序。
2. 任一方案出现以下情况时，不得直接成为最终推荐方案：基态潮流不收敛；短路电流超过断路器开断能力；最小断路器开断裕度率 < 0；关键设备负载率超过硬约束；其他 compare_rules 安全硬约束不满足。
3. 若**所有方案**均违反安全硬约束：必须写明“当前没有可直接推荐实施的方案；所有方案需整改后重新仿真校核”；可以给出“经济性排序第一的整改优先候选方案”，但不得称为“最终推荐方案/建议优先实施”。
4. 禁止写：“短路超标是共性问题因此不影响推荐”“虽然不满足安全要求仍建议优先实施某方案”。共性安全问题仍是淘汰条件。

# 输出格式
- 直接以Markdown格式输出报告，按照要求解释计算结果。
- 正文以完整段落为主；仅在报告摘要、风险清单和整改建议中使用短列表，避免整篇报告堆叠项目符号。
- 公式、计算方法、指标定义必须写成普通段落、行内公式或 `$$...$$` 数学块；不得使用三反引号代码块包裹公式或说明文字。三反引号只允许用于真正的程序代码。

## Markdown 安全规则
- 当普通比较符号 `>` 或 `<` 出现在列表项、表格单元格或一行文本的开头时，必须转义为 `\>` / `\<`，或改写为中文“大于/小于”，避免被 Markdown 解析为引用块或 HTML 标签。
- 正确示例：`- \>95%：可用良好；`、`- \<90%：风险较高；`。
- 禁止示例：不得直接写成 `- >95%：可用良好；`，因为 `>` 会被 Markdown 当作引用块标记吞掉。
